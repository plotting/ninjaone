# MFA Enrollment Posture Audit — NinjaOne Automation

Built 2026-08-25, following the `bit-ninjaone-automation` skill process. Report-only automation that audits Entra ID MFA enrollment posture per user per Client tenant, resolved via Partner Center, written into NinjaOne **organization-level** custom fields. Explicitly mirrors the Entra Role Assignments Audit (v2.1) architecture and, per Jeff's direct request, reuses that automation's Client↔tenant mapping field and shared credential fields rather than creating new ones.

## Origin

Jeff asked for something similar to the Entra Role Assignments Audit but for MFA posture, and supplied an example Partner Center MFA/licensing PowerShell script (per-org, interactive customer selection, CSV export to `C:\Temp`) as a starting point, with the instruction to reuse the existing secrets/mapping fields rather than duplicate them. The Entra Roles doc's own "Open follow-up" section had flagged this exact question ("Whether/when to fold MFA registration status into this same report — not built yet") — this build answers it: **a separate script, not folded into the Entra Roles report**, but sharing its mapping and credentials.

## Scope decisions confirmed with Jeff (via AskUserQuestion)

- **Graph app**: same multi-tenant app registration as Entra Roles (client ID `65343291-651c-48c9-bfce-85b17b41e949`) — reuses `Entra Roles Graph Client Secret`. Needs `UserAuthenticationMethod.Read.All` added to that app's existing application permissions (alongside `User.Read.All` + `Directory.Read.All`) and re-consented per customer tenant.
- **Poor-posture definition**: a user counts as poor MFA posture if they have **no registered non-password method, or only SMS/phone call**. (The alternative considered was "no methods only.")
- **Scheduling**: runs on the **same centrally-scheduled utility device/schedule as the Entra Role Assignments Audit** — a separate script, not merged into Entra Roles' script, but not a second utility device either.

## Architecture

Central script (`Set-MFAPostureAudit-NinjaOrg.ps1`), same pattern as Entra Roles v2.1: authenticates to the NinjaOne API once (shared app/credentials) → GETs all organizations → for each org, reads the **shared** `Entra Roles Partner Center Org Name` field (owned by Entra Roles, not duplicated here) → if blank, attempts the identical exact-name auto-match logic Entra Roles uses (writes back on an unambiguous match only) → resolves the Partner Center tenant → Graph pull of every user's `authentication/methods` → classifies posture (None / Weak / Adequate) → builds an HTML report of every non-excluded None/Weak user, worst-first → PATCHes `MFA Posture Report`, `MFA Posture Poor Found`, and `MFA Posture Changelog` via the NinjaOne API. A single organization's failure is logged and skipped, never fatal to the run — only a total inability to start (credential/auth failure) exits non-zero.

Unlike the AD Stale Users argument-length bug (Bug #5 on that build), this script's Organization-level writes go through `Invoke-RestMethod -Body` (API PATCH), not `Ninja-Property-Set`'s command-line invocation — so it isn't exposed to that specific OS argument-length ceiling. It still budgets the report (`$ReportBudgetChars = 150000`) to stay under NinjaOne's own ~200,000-character WYSIWYG storage ceiling, since a whole-tenant per-user report can still be large. Rows are dropped worst-last (SMS/phone-only rows drop before any no-MFA row) if the budget is hit.

PowerShell 5.1 collapse-safety patterns applied preventively throughout (same bug family as Entra Roles/AD Stale Users): `@(...)` wrapping on `Where-Object` results and array-returning functions, `return ,$var` for non-array enumerables, no array-typed parameter marked `Mandatory`. Finding #6 extended this family (a Mandatory `[string]` parameter also rejects an empty string, not just `$null`). **Finding #7 adds an observability layer on top**: a diagnostic HTTP-error-body extractor (`Get-HttpErrorResponseBody`), a positive per-org "wrote fields" success log line, and reduced per-user progress-log frequency (every 250 users, not 50) to cut total output volume on large tenants.

## Custom fields

| Field name | Type | Level | Purpose |
|---|---|---|---|
| Entra Roles Partner Center Org Name | Text | Organization | **Reused, not created.** Owned by the Entra Role Assignments Audit automation. This script reads/writes it exactly as Entra Roles does (including auto-match) rather than creating a second mapping field. |
| MFA Posture Allow List | Text | Organization | New. READ. UPNs excluded from poor-posture flagging (break-glass/emergency-access accounts, service/shared mailboxes that can't register MFA) — one per line. |
| MFA Posture Report | WYSIWYG | Organization | New. WRITE via NinjaOne API. Lists every non-excluded user with no MFA method or SMS/phone-only, worst-first, with a scan summary line at top. |
| MFA Posture Poor Found | Checkbox | Organization | New. WRITE via NinjaOne API. True when ≥1 non-excluded user has no MFA method or SMS/phone-only — this is what the alert condition watches. |
| MFA Posture Changelog | Multi-line text | Organization | New. READ+WRITE via NinjaOne API. Per-run history, capped at 200 lines. |
| Entra Roles Partner Client Secret / Entra Roles Graph Client Secret | Secure | Global | **Reused, not created.** Same as Entra Roles. Graph app now also needs `UserAuthenticationMethod.Read.All`. |
| ninjaoneInstance / ninjaoneClientId / ninjaoneClientSecret | Text/Secure/Secure | Global | **Reused, not created.** Same NinjaOne API app as Cove/Entra Roles. |

## Key decisions

- **No new Global Secure fields at all** — every credential this script needs already exists from the Entra Roles build. The only NinjaOne-side prerequisite is adding one Graph API permission to the existing app registration.
- **Separate script, shared schedule/device** — keeps the two automations independently deployable/failable while avoiding a second utility device or a second mapping field.
- **Poor posture = None or Weak (SMS/phone-only)**, a single combined flag/report criterion per Jeff's decision — not two separately-configurable thresholds.
- **Report lists only flagged users**, not the full roster (unlike Entra Roles' role-assignment report, which lists everyone) — a whole-tenant user list would be far larger than the flagged subset, so scoping the report to None/Weak users keeps it directly actionable and keeps the size budget meaningful.
- **Allow list is new** (Entra Roles has none, by design — it's report-only with no flagging concept). MFA posture needed one because break-glass/emergency-access accounts and service/shared mailboxes are expected, legitimate no-MFA cases that would otherwise always show as flagged.
- Two hardcoded Partner Center values (`$PartnerClientId`, `$PartnerTenantId`) are left as placeholders in the delivered script with an explicit instruction to copy them verbatim from the Entra Roles script — this session did not have that script's file contents available to confirm the real values, only the architecture description in its own project doc.

## Rollout findings (real production incidents)

1. **First live run: failed at startup with `ERROR: Missing required Global credential field(s): ninjaoneInstance`.** RESOLVED. The script's own startup validation caught this correctly — checked all five required Global fields together and named exactly the one that was blank. Since `ninjaoneClientId`, `ninjaoneClientSecret`, `entraRolesPartnerClientSecret`, and `entraRolesGraphClientSecret` were *not* flagged, those four were already populated. Not a script bug — the `ninjaoneInstance` Global field simply had no value yet (the NinjaOne API instance hostname). Jeff populated it and re-ran.
2. **Second live run: passed startup, failed with `ERROR: Could not authenticate to Partner Center - aborting run.`** RESOLVED — root-caused before the run, not discovered by the log alone. The delivered script shipped with `$PartnerClientId`/`$PartnerTenantId` as literal placeholder strings (`"<COPY-FROM-ENTRA-ROLES-SCRIPT>"`), documented as needing manual replacement from the real Entra Roles script. Substituting that literal string into the OAuth token URL's tenant segment fails immediately. Jeff filled in the real values and re-ran.
3. **Third live run: NinjaOne API auth succeeded, Partner Center auth succeeded (252 customers cached), 1 NinjaOne organization found ("Internal Testing Org") — then crashed processing it: `Cannot process argument transformation on parameter 'OrgId'. Cannot convert the "System.Object[]" value of type "System.Object[]" to type "System.Int32".`** Superseded by finding #4/#5 below — the underlying response-shape confusion is the same family of bug across findings #3–#5, just diagnosed in stages as more real data came in from successive live runs.
4. **Fourth live run (with a diagnostic-dump patch): SUCCESS at the script level. The `DEBUG:` log line showed the raw response as `{"value": [ {org}, {org}, ... ]}`,** which was read at the time as proof `/v2/organizations` always wraps results in a `"value"` property. `Get-NinjaOrganizations` was changed to always unwrap `.value`. **This turned out to be an overcorrection — see finding #5.**
5. **Fifth live run (with the `.value`-unwrap fix applied): the run no longer crashed, but every single organization failed with `org.id is null`, despite `Found 160 NinjaOne organizations` — a plausible real count.** RESOLVED — root cause reproduced and confirmed in isolation. `/v2/organizations` does **not** reliably return one single shape — this run's response was itself already a bare array of 160 org objects (no `"value"` wrapper). `Get-NinjaOrganizations`, after finding #4's fix, unconditionally accessed `.value` on that response. Because PowerShell performs **member enumeration** when a member is accessed on a collection rather than a single object, `$response.value` on an already-bare array silently returned an array of `$null` — one per organization, since none of the org objects actually has a `"value"` property — instead of erroring.
   - **Fix**: `Get-NinjaOrganizations` now branches on the actual response: if `$response` is itself a PowerShell array, it's used as-is; else if it has a `"value"` property — checked via `.PSObject.Properties.Name`, never via dynamic `.value` member access — it unwraps `.value`; else it's treated as a single bare organization object. A `DEBUG:` log line reports which shape was detected every run.
   - **Verified** against all five shape variants using the real function body in a mock harness.
   - **Still open, unconfirmed either way:** pagination for `/v2/organizations`. 160 could plausibly be either the true count or a page cap.
6. **Sixth live run (with finding #5's fix applied): the org-fetch step worked correctly — real data for all 160 organizations, several large tenants fully scanned (YMCA of Greater San Antonio: 1,327 users, 883 flagged, 408 rows omitted for budget; Cavender Auto Family: 2,259 users, 655 flagged, 196 rows omitted).** But every organization that got that far then failed on the same line: `Cannot bind argument to parameter 'ExistingChangelog' because it is an empty string.` RESOLVED — a brand-new `MFA Posture Changelog` field, never written to before, reads back from the NinjaOne API as `""`, not `$null`, and a `Mandatory [string]` parameter rejects an empty string just as readily as `$null`.
   - **Fix**: added `[AllowEmptyString()]` to `Add-ChangelogLine`'s `$ExistingChangelog` parameter. Verified against empty string, `$null`, and a real multi-line changelog.
   - **Impact**: blocked every field write that run — zero organizations got their fields updated, even though scanning worked.
7. **Seventh live run (with finding #6's fix applied): real progress — YMCA and Cavender Auto Family both completed their full scan-and-write cycle with no bind error this time** (the empty-string fix held), and the run reached several more organizations before the pasted log cut off mid-line during Biodynamic Research Corporation's processing. Jeff asked whether the run had timed out. Two things surfaced from this run, one genuinely new and one investigative:
   - **New symptom, not yet root-caused: Hill Associates failed with `The remote server returned an error: (400) Bad Request.`** This is a different failure from finding #6 (no empty-string message this time) and happened right where `Set-NinjaOrgField`'s PATCH call would run, after the scan and report build both completed cleanly (75 flagged, no budget-omission WARN, so report size is very unlikely to be the cause). The script's error logging only ever surfaced the generic `.Message` text ("(400) Bad Request") from `Invoke-RestMethod`'s exception — never the actual response body, which is where NinjaOne's specific validation reason would be. **Rather than guess at the cause, added `Get-HttpErrorResponseBody`**, a diagnostic helper that extracts and logs the real response body text (via `$_.ErrorDetails.Message`, falling back to manually reading `.Exception.Response`'s stream) immediately before `Invoke-RequestWithRetry` re-throws a non-retryable error. This mirrors the same "add diagnostics, don't guess-fix" approach that got findings #4/#5 root-caused. **Caveat, stated plainly rather than overclaimed**: this was only testable against pwsh 7.4.6 in this session's sandbox, where `Invoke-RestMethod`'s error shape differs from Windows PowerShell 5.1's (production environment) — confirmed the helper never crashes regardless of exception shape or PS version, but its ability to actually *extract* a body on real PS 5.1 is unverified since no PS 5.1 runtime was available to test against. If the next run's WARN line for Hill Associates (or any other 4xx) still shows no extra detail, that's the sign this needs a different extraction approach for PS 5.1 specifically.
   - **Investigative, re: "did it time out?"**: the run's own header still read `Result: SUCCESS` (same as every prior run, including ones with individual org failures) — that field only reflects whether the *script process itself* exited non-zero, which only happens on a startup-level failure, not a per-org one, so it doesn't by itself prove the run reached its final "Run summary" log block. Two explanations are plausible and not mutually exclusive: (a) the platform truncated the *pasted/displayed* output before the run's actual end — this platform has done exactly that before, cutting off the finding #4 DEBUG JSON dump mid-string — or (b) the run was genuinely still in progress or got killed by a configured script/action timeout. **Not resolved this round** — pending Jeff checking directly in the NinjaOne console (see Open follow-up) rather than being guessed at from the paste alone. In the meantime, cut total log volume to make future truncation less likely and easier to diagnose: reduced per-user progress logging from every 50 users to every 250, and added an explicit `Wrote fields for {org} (...)` success line after every completed write, so a future run's log makes it possible to tell exactly how far processing actually got even if the pasted output is incomplete.
