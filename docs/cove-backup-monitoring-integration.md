# Cove Data Protection backup monitoring integration (2026-08-17, updated 2026-08-19)

## What this is

Jeff brought in a two-script Cove (N-able) Data Protection ↔ NinjaOne integration and asked for it to be built out properly: script review/fixes, deployment guidance, and the paired SOP + Runbook per the `bit-ninjaone-automation` process. Confirmed via AskUserQuestion: full build, and the org-rollup script runs as a NinjaOne automation, not on an external PC.

Since then this has grown through several rounds of live-data troubleshooting with Jeff: card readability, an M365 per-workload breakdown, two real hostname-matching bugs, a full correction of the device-tagging design (including two real production runtime failures), NinjaOne-specific device deep-linking, splitting out devices that are Cove-protected but missing from NinjaOne entirely, and — as of 2026-08-19 — a chronic-stale-device ticket trigger (which itself surfaced and fixed two more real production bugs, plus three rounds of scope/wording refinement once Jeff saw real output, converging on a clean separation between two previously-conflated concepts: "not in Cove at all" vs. "in Cove but stale").

## Three scripts (as of 2026-08-19)

1. **`Set-CoveBackupStatus-Ninja.ps1`** — runs on Cove-protected endpoints, reads `ClientTool.exe` session data, writes a per-device WYSIWYG card (`Cove Backup Status`) + plain-word result (`Cove Backup Result`). CardTheme fixed to `light`; briefly grew tag-management logic that was reverted back out (see "Device detection tagging" below) — it only builds the status card now.
2. **`Set-CoveBackupRollup-NinjaOrg.ps1`** — runs centrally, calls the Cove Partner API + NinjaOne public API, writes an organization-level WYSIWYG roll-up (`Cove Backup Rollup`) per Client Organization, plus (new 2026-08-19) two chronic-stale-device fields per org. Has seen the most iteration — see all sections below.
3. **`Set-CoveDetectionTag-Ninja.ps1`** — lightweight, no-API, fleet-wide detection script — see "Device detection tagging" below. Corrected 2026-08-18 to actively probe for the real local tag mechanism rather than assume one (see "Two real production runtime failures").

## Real defect found by comparing against the Entra script (fixed 2026-08-18)

The Entra script's setup notes state its `ninjaoneInstance` / `ninjaoneClientId` / `ninjaoneClientSecret` fields are **Global** and are "the SAME Global fields the Cove roll-up automation already uses." That wasn't true as originally built (Device-scoped, tied to one designated runner). Fixed: all seven credential fields are now Global-scoped, removing the "must run on one specific device" constraint.

## Auto-match feature: `Cove Customer Match`

Organization-level field (Text, API Read/Write) that auto-resolves and persists a NinjaOne Organization → Cove customer name mapping (exact normalized match, human-overridable), used only to place cloud/M365 Cove backups with no matching NinjaOne device. **Deliberately name-only, not ID-based** — `EnumerateAccountStatistics`'s common query path doesn't attach a stable per-device customer/partner ID to its rows, so an ID option would silently only work on the rare fallback path. Told Jeff directly rather than shipping something fragile.

## Live deployment troubleshooting (2026-08-18) — root cause found and fixed

First live run failed with `Missing credential 'Cove Password'` despite the Global field showing a populated value. Root cause: **the field had only just been created/permissioned minutes before the failing run** — re-running after the permission settled resolved it. No script change needed; a timing gotcha worth remembering for future NinjaOne Global/Secure field rollouts.

## Card rendering fix (2026-08-18): dark-theme text on a light card — both original scripts

The org roll-up card and the device-level status card both defaulted `$CardTheme = 'dark'`, which uses near-white text (`#e6edf3`/`#c9d1d9`) meant for NinjaOne's dark console — but both cards render on a white background panel in practice. Fixed both scripts' default to `$CardTheme = 'light'` (dark text, `#1f2328`/`#57606a`). Status pills were unaffected (separate saturated color map).

## Microsoft 365 per-workload breakdown (2026-08-18)

The old "Cloud / M365" section was a generic catch-all — any Cove account that didn't hostname-match a NinjaOne device got labeled "Cloud" with no verification it was actually M365. Researched Cove's JSON-RPC column-code reference (`developer.n-able.com/n-able-cove/docs/column-codes`) and found a real way to confirm and enrich M365 accounts:

- **`I59`** (Account type) — value `2` confirms genuine M365.
- **`D19`/`D20`/`D05`/`D23`** — Exchange / OneDrive / SharePoint / Teams datasource codes.
- **`<datasource>F00`/`F02`/`F06`/`F15`** — per-workload last-session status, processed-item count, error count, timestamp.

Implemented in `Set-CoveBackupRollup-NinjaOrg.ps1`: `Get-CoveDevices` requests all these columns; `ConvertFrom-CoveRow` builds an `AccountType` + `Workloads` array; the cloud-placement loop emits one row per protected M365 service (`Type = "M365 Exchange"` etc.) with a `SizeLabel` processed-item count instead of a byte size, mirroring the Cove console's own per-service session history (confirmed against a screenshot Jeff provided). Non-M365 accounts keep the original generic "Cloud" row (later split further — see "Not in NinjaOne" below). `New-SectionTable`/`New-DeviceRowsHtml` gained per-section `ShowType`/`SelectedLabel` overrides so this section shows its Type column without affecting Servers/Workstations.

## Two real bugs found from Benson Enterprises' live data (2026-08-18, both fixed)

**1. Hostname-matching gap — Device name vs Computer name.** Cove's "Device name" (its `AN` column, a console-editable label) and "Computer name" (the real OS hostname) are NOT reliably related — e.g. Device name `chryslerparts16_ys4fz` for Computer name `CHRYPARTS`, or `finance16_g9kv0` for `GM2`. The script was only matching on Device name, so 10 real, actively-backed-up servers were wrongly showing under "Servers with NO backup." Fixed: added Cove's `I18` column (true Computer name) to the query; `$coveByName` now indexes Computer-name keys first (more reliable), Device-name keys second as fallback.

**2. Stale "ghost" Cove accounts showing as fake Cloud/M365 rows.** After fix #1, two devices (FILESERVER, DOCUMENTATION) that matched correctly and showed current status in the Servers section *also* appeared a second time under "Cloud / M365" with wildly stale data (over a year old) and generic `Cloud` type. Root cause: a second, old/duplicate Cove account shares the hostname of a device that already has a fresher, correctly-matched account — likely left over from a past reinstall/re-enrollment where Cove created a new account instead of reusing the old one. Fixed: built `$ninjaKeys` (all NinjaOne server/workstation hostname keys) unconditionally; the cloud-placement loop now skips any Cove account whose own hostname matches an already-covered NinjaOne device, logging it as a skipped "ghost" account rather than surfacing it as misleading Cloud noise.

## Device detection tagging (2026-08-18) — design corrected, then hardened against two real production failures

Jeff wants the heavier `Set-CoveBackupStatus-Ninja.ps1` scheduled against only Cove-protected devices instead of the whole fleet. **First attempt (wrong, reverted):** tag-set/tag-clear logic was put directly inside `Set-CoveBackupStatus-Ninja.ps1` itself. Jeff corrected this immediately: *"No I wanted the universal script to tag the devices if they exist in Ninja so I only have to run the Cove script against those if possible"* — running the heavy script fleet-wide just to find out which devices to tag would defeat the entire point of scoping it down.

**Correct design, implemented:** split detection into its own script, `Set-CoveDetectionTag-Ninja.ps1` — does nothing but check for `ClientTool.exe` (a couple of `Test-Path` calls + a CIM service-path fallback, no Cove/NinjaOne API calls) and tag/clear `"Cove Protected"`. Cheap enough to schedule against the *entire* fleet on a daily cadence. `Set-CoveBackupStatus-Ninja.ps1` had its tag-management code removed again — it only builds the status card. Once devices have run the detection script at least once, Jeff can build a dynamic device group / policy filter on the `Cove Protected` tag and point the heavier status script's schedule at just that group.

**Two real production runtime failures, both hit live and both fixed:**

1. **`ninjarmm-cli` not recognized.** Initial documentation research (via WebFetch) indicated the local tag command was a standalone `ninjarmm-cli tag-set`/`tag-clear`. A real scheduled run failed with "The term 'ninjarmm-cli' is not recognized." Notably, a second WebFetch of the *exact same* documentation URL later returned a different (and ultimately correct) answer — flagged directly to Jeff as evidence that WebFetch's AI summarization isn't reliable for pinning down exact CLI/cmdlet syntax on this kind of page. Fixed by rewriting `Set-CoveDetectionTag-Ninja.ps1`'s tag logic around a `Find-NinjaTagMechanism` function that actively probes the device for whatever mechanism actually exists — candidate injected cmdlets (`Set-NinjaTag`/`Remove-NinjaTag` and others), a bare `ninjarmm-cli` on PATH, and a filesystem search under the NinjaRMMAgent install folders — rather than hardcoding a guessed name.
2. **`Set-NinjaTag : Undefined field`, with a misleading false-success log line.** A later real run confirmed the probe found the right mechanism (`Set-NinjaTag`/`Remove-NinjaTag`, PowerShell cmdlets injected by the agent — NOT a CLI exe), but the call itself failed with "Undefined field," and — because these cmdlets report failure via a non-terminating `Write-Error` rather than a thrown exception — the surrounding `try/catch` didn't catch it, so the script printed a false "Tag ... set via Set-NinjaTag/Remove-NinjaTag" success line right after the real failure. Root cause, confirmed with Jeff: the `Cove Protected` tag hadn't been created yet in NinjaOne (Administration > Devices > Tags) — the cmdlet can assign/clear an *existing* tag, it cannot create the tag definition. Fixed by adding `-ErrorAction Stop` to the cmdlet invocation so the error becomes terminating and is actually caught. **Confirmed ground truth for this tenant's agent build: the real local tag mechanism is the `Set-NinjaTag`/`Remove-NinjaTag` PowerShell cmdlets, not `ninjarmm-cli`.**

Jeff still needs to create the `Cove Protected` tag once under Administration > Devices > Tags before either script's tagging does anything (confirmed directly with Jeff — yes, it must be created manually first).

## NinjaOne asset deep-linking (2026-08-19)

Device name links in the roll-up card previously pointed at a generic Cove console URL, not the specific machine. Jeff asked for either a device-specific Cove link or a direct NinjaOne asset link. Implemented the NinjaOne option: added `Get-NinjaDeviceDashboardUrl` (calls `GET /v2/device/{deviceId}/dashboard-url`, parsing whichever response property comes back — `url`/`dashboardUrl`/`deviceDashboardUrl`/`link`/`href` — defensively, since the exact field name wasn't independently confirmed) with a cache, and rewrote `Link-Device` to try the NinjaOne dashboard URL first (via the row's `NinjaDeviceId`, now captured during device enrichment) before falling back to the old Cove console URL template for rows with no NinjaOne match.

## Splitting real "not in NinjaOne" devices from true Cloud/M365 (2026-08-19)

Adding the NinjaOne asset links surfaced something important: many rows in the "Cloud / M365" section for the Aftermarket Alliance org (Jeff: *"I still don't understand why obvious workstations are tagged as cloud/m365 still"*) turned out, once linked, to have no NinjaOne asset at all — they were real Cove-protected devices that simply don't exist as a device record in NinjaOne yet, not actual cloud/M365 accounts. Jeff confirmed directly: *"Adding the Ninja URL 100% confirmed if the device doesn't exist in Ninja you're tagging it as Cloud/M365 too."*

Fixed in `Set-CoveBackupRollup-NinjaOrg.ps1`: for Cove accounts with `AccountType` other than `2` (M365), the row now gets `Type = 'Not in NinjaOne'` (was previously always generic `'Cloud'`) when `AccountType -eq 1` (Backup Manager, i.e. a real endpoint), reserving `'Cloud'` for accounts that genuinely aren't a recognized endpoint type. `Build-Sections` now emits these as their own section — **"Cove-protected, not in NinjaOne"** — inserted before the real Cloud/M365 section, so the two are never conflated again. Summary log line now reports both counts separately plus the ghost-account skip count.

## Chronic-stale-device ticket trigger (2026-08-19)

Jeff, looking at the new "Cove-protected, not in NinjaOne" section: *"Now for these can we trigger at the org level to create a ticket about an org having a device that doesn't have a backup within the last 6 months?"* Clarified via AskUserQuestion — confirmed answers: (a) trigger mechanism = a NinjaOne Condition on an Organization custom field (the script does NOT call ConnectWise directly), (b) granularity = one summary ticket per org listing all stale devices, not one per device.

Implemented in `Set-CoveBackupRollup-NinjaOrg.ps1`:

- New settings: `$ChronicStaleDays = 180` (~6 months), `$ChronicStaleCountField = 'coveChronicStaleCount'`, `$ChronicStaleSummaryField = 'coveChronicStaleSummary'`, `$ChronicStaleSummaryMax = 20` (soft cap on how many device names go into the summary text before line-count truncation kicks in).
- `Get-ChronicStaleInfo` — given an org's rows, finds stale devices and builds a count + a newline-joined text summary (name, type, last-backup status/age), truncated with an "...and N more" line past the cap. Filtering logic went through three rounds of correction after Jeff reviewed real output — see below for the final, correct rule.
- `Set-ChronicStaleFields` — writes both values to the two new Organization custom fields, gated on `$WriteToNinja`.
- Wired into both execution branches: the per-org branch calls it once per org right alongside the existing WYSIWYG card write; the global (`$Scope -eq 'global'`) branch — where the *card* is consolidated onto one tenant-wide field — still loops every real org separately for this, since the stale-device ticket has to land on the org that actually owns the device.

**Two more real production bugs found and fixed once Jeff ran this live (2026-08-18/19):**

1. **Hidden error bodies on every NinjaOne API failure, tenant-wide.** The Summary field started failing with a generic "(400) Bad Request" and no further detail, for a seemingly random subset of orgs. Root cause, found by inspecting `Invoke-Ninja`'s error handling: NinjaOne automations run under pwsh (PowerShell 7+), where a failed `Invoke-RestMethod` throws `Microsoft.PowerShell.Commands.HttpResponseException` — its `.Exception.Response` is a `System.Net.Http.HttpResponseMessage`, which has **no** `GetResponseStream()` method (that only exists on the older `System.Net.HttpWebResponse`/`WebException` shape from Windows PowerShell 5.1). The existing error handler tried to call it anyway inside an empty `catch {}`, so the real response body was being silently discarded — meaning **every** 400 this script has ever logged (not just this feature) has shown only the generic wrapper text, never the actual reason. Fixed `Invoke-Ninja` to read `$_.ErrorDetails.Message` first (populated by `Invoke-RestMethod`/`-WebRequest` on an HTTP error response on both PS5.1 and PS7+), falling back to the old stream-read only when the response object actually exposes `GetResponseStream`. This one fix benefits every API call this script makes, not just the chronic-stale fields.
2. **`coveChronicStaleSummary` hitting an undocumented NinjaOne field length limit.** With the real error body now visible, the exact cause came through: `{"resultCode":"attribute_value_max_length_exceeded","errorMessage":"Max length exceeded"}`. Orgs with only 1-3 stale devices wrote fine; orgs with more (Bridgehead I.T., XPEL Inc., ValMark Chevrolet, JMJ Associates, etc.) failed outright, meaning the field's real max length is well under what a full device list can produce even after the existing 20-line cap. Fixed by adding `Set-NinjaOrgFieldWithLengthFallback`: tries the full summary, and on that specific `attribute_value_max_length_exceeded` response (not any other error), halves the text and retries, repeating until it fits or falling back to a guaranteed-short fallback message. Any other error is logged and not retried, since shrinking won't fix it. `Set-ChronicStaleFields` also now logs Count and Summary failures as two independent try/catch blocks so future log output says exactly which field failed and why, instead of one ambiguous shared message.

**Three rounds of scope correction, all on 2026-08-19, converging on the final model:**

1. **Round 1 — Servers only (too strict one way).** The Summary field, once populated, was full of workstation noise — personal laptops and Mac endpoints (`Ashs-MacBook-Air.local`, `BIT-JEFFB`, `Chris-Gs-MacBook-Pro.local`, etc., many of them Bridgehead's own internal machines) that were never intended to be Cove-protected in the first place, all showing as "chronic stale" simply because they had no Cove data at all. First fix: filtered to `Type -eq 'Server'` only, and changed wording to say "Not Being Backed Up" for a device with no Cove data, vs. `last backup: <age>` for one that had backed up before but gone stale.
2. **Round 2 — Servers-only over-corrected (too strict the other way).** Testing against Aftermarket Alliance Auto Parts showed this dropped a real signal Jeff wanted: a Cove-protected *workstation* that's gone stale (e.g. `LTMMARTINEZ3651`, last backup 2025-10-07, Warning status) should still be flagged. Jeff: *"I want to alert on stale workstations but ONLY if they're actually being backed up... I DONT want to report workstations not being backed up unless they are in Cove and failing."* Fixed with asymmetric per-Type logic: Server flagged with or without a Cove match; Workstation flagged only if Cove-matched AND stale.
3. **Round 3 (final) — realized the asymmetric Server/Workstation split was still the wrong axis entirely.** Jeff clarified the actual mental model directly: *"Stale should be ANYTHING in Cove without a backup in the last 6 months period[.] Servers not being backed up shouldn't be Stale, they should show here [the existing 'Servers with NO backup' card section]: with something other than 🚫 No Backup, same concept but Not Backed Up by Cove more clearly I guess[.] I don't care if a workstation is in Ninja and not being backed up by cove but if it's in Cove I want to know if it's stale."* This reframes the whole feature as **two genuinely separate concepts** that rounds 1-2 kept conflating:
   - **"Not backed up by Cove"** — a device has no Cove match at all (never enrolled). This is NOT staleness; it's a completely different situation, and it already has its own card section ("Servers with NO backup" / the `'None'` status). Renamed that status's label in `Get-StatusStyle` from the ambiguous **"No Backup"** to **"Not Backed Up by Cove"** so it never reads as a staleness signal.
   - **"Stale"** — a device that IS in Cove (`HasBackup`) but hasn't had a successful backup within `$ChronicStaleDays`. This is the ONLY thing the ticket-trigger fields should measure, and it applies uniformly to every Type (Server, Workstation, Cloud, M365, "Not in NinjaOne") — there's no Server/Workstation asymmetry needed once the "not enrolled at all" case is fully excluded, since a device with no Cove match already fails the `HasBackup` check on its own.

   `Get-ChronicStaleInfo` simplified to a single universal rule: `HasBackup -and (no Last, or Last older than $ChronicStaleDays)`, dropping all Type-based branching from rounds 1-2. Wording in the minimal length-fallback message and the log line generalized from "server(s)" back to "Cove-tracked device(s)," since scope is no longer Server-specific.

Script re-validated (`ParseFile`, clean) and re-delivered to Jeff after each of these fixes.
